# Hosted CSV acceptance on an unused Online Retail date

This protocol defines one prospective Chrome acceptance run against a verified ProofFlow release at `https://proofflow.arnavbule.in`. It exercises actual file upload, an authored exchange-rate correction, stale export refusal, refresh and browser reload using earlier-unused transaction lines. It measures automated behavior on one daily partition and one demo host. This design provides no human usability, customer adoption, generalization across datasets or load measurements.

Scan the workbook in chronological order and use the **first unreserved date that has between 1 and 1,000 eligible lines**. Keep every eligible line for that date in worksheet order. Verify that no invoice for that date appears in any reserved partition, using the entire original rows on reserved dates and months. If it overlaps, if the CSV exceeds 1 MiB, or if another preparation requirement fails, stop. Choose the report country with the most eligible lines, using lexical country order to break ties. The choice uses dates, line counts and source identity only.

Interpret the workbook date serial in the Excel 1900 system and take its calendar day. Trim invoice and country text. Exclude cancellation invoice numbers (prefix `C`, case-insensitive), missing or unsupported invoice/country identifiers, nonpositive, nonfinite or nonintegral quantities and nonpositive or nonfinite prices. Quantities are bounded at 1 billion. A country must fit in 64 characters with no control character or `__` prefix, and its derived order ID must fit in 200 characters with no control character. Read numeric cells using binary64 and the shortest round-trip decimal string, consistent with the previous retail fixtures. Retain only lines for which `Decimal(quantity) × Decimal(unit price) × 100` is exactly integral and within 1–10¹² pence. No line amount is rounded to qualify.

All eligible rows are from the United Kingdom, so both report totals coincide for this fixture. The 28,429-byte upload contains only `order_id,region,currency,gross_cents`. Its IDs are `uci:<InvoiceNo>:row:<original worksheet row>`, and its currency is `GBP`. The dataset is a positive-sales extract. The CSV supplies no refunds or support observations and the import defaults the omitted fields to zero. The monetary values describe this extract rather than a complete merchant ledger. The exchange rates **1.25 → 1.30 GBP/USD** are authored solely for this experiment, independent of the workbook's transactions.

## Independent expected values

The standalone Decimal oracle reads each original quantity and price cell from sanitized provenance, applies the documented binary64 decoding, and adds GBP subtotals by country. For each stage it converts the entire GBP amount of each country to USD, rounds to the nearest cent with ties to even, then adds the resulting country cents for the company total. The oracle does not import application calculations or read the prepared `gross_cents` values. The source scan preparation reuses only the hash-checked worksheet reader. The offline audit also reconciles every uploaded line against its original cells. [Frozen source hashes, audit and values](../fixtures/real_partition_v1/fixture.json).

The source lines sum to **£7,242.06**. The initial product `7242.06 × 1.25` is `9052.575`, yielding **$9,052.58**. The corrected product `7242.06 × 1.30` is `9414.678`, yielding **$9,414.68**. The United Kingdom and company each have **905,258 USD cents** before and **941,468 USD cents** after the correction. Half-even and half-up rounding agree on these two inputs. While stale, both current values must be JSON `null` and the UI must show **Awaiting refresh**. The prior amounts may appear only as historical amounts.

## One measured run

The manual workflow uses one fresh Chrome context on GitHub-hosted Ubuntu 24.04, system DNS, normal TLS validation and two tabs of that same context. Before the measured run, commit the reviewed protocol, fixture, audit, runner, tests and workflow. The operator verifies the exact deployed source revision and Linux image ID independently via the host delivery receipt. Enter those IDs and the freeze commit at dispatch. Preflight checks that the clean checkout has identical probe files to the freeze and identical Docker inputs to the named release, rebuilds assets with the locked dependencies, and matches served HTML and referenced JavaScript/CSS byte for byte before creating a browser session. The browser receipt does not independently attest the running image ID.

1. **Release preflight.** Verify the clean GitHub checkout, recorded freeze and release identities, direct canonical-host resolution without a hosts override, public health via HydraDB OSS, and exact released frontend bytes.
2. **Upload, preview and create.** Open the app over TLS and allow its startup `POST /api/session` to create the fresh guided session and set its secure cookie. Upload the frozen `orders.csv` using the file input and supply GBP/USD 1.25 and the selected country. Preview reports the exact file hash, 642 rows, GBP, the selected country, no ticket regions, eight validation calculations and zero recorded tool calls. Import state is still absent after preview. Create both reports and check oracle amounts in the API and UI, native HydraDB operation, and accounting of eight preflight, eight recorded and 11 verification calculations.
3. **Initial checked export.** Click the download control. Require HTTP 200, no-store headers, matching visible report heads in the request, and a browser download byte-identical to the server-checked UTF-8 content. Check both values, both paired report and claim IDs, and a recent UTC check time. Require the export to omit session secrets and raw CSV lines.
4. **Publish correction and attempt old export.** Open a second tab from the first tab and upload the identical CSV. Preview again, change only GBP/USD to 1.30, and publish. Require one changed FX source version, no new artifact heads at publication and exactly four identified descendants: regional conversion, company total and both reports. Require eight preflight calculations and zero recorded or verification calculations. The original tab retains its last view until it attempts export. Click its download control once and require its original generation and report IDs in the request, HTTP 409 `evidence_unavailable`, no download event and API/UI reconciliation to withheld current values with historical labeling.
5. **Refresh and export corrected reports.** Refresh once from the original tab. Require two correct current values, four recorded executions (conversion, company total and two compositions) and 11 verification calculations. Check replacement of precisely the four affected heads and unchanged gross GBP, refunds, net GBP and support heads. Verify a second checked download against the new report/claim pairs and corrected amounts under the same rules as the initial download, and confirm that the first file's bytes remained unchanged.
6. **Reload.** Reload the original page and check the corrected UI values plus the same session, generation, source versions, report IDs and all artifact heads. Require exactly two successful downloads and no JavaScript runtime error.

The job has a seven-minute budget and a 30-second timeout per browser action/request. The run allows one startup session POST, two validation previews, one import create, one update, one refresh and three export requests. The browser sends these nine requests in the order specified above and the harness records attempts before network dispatch, including blocked or failed requests. The browser guard blocks unexpected same-origin API writes and refuses all later writes after any deviation. Browser assertions wait for expected UI states. No mutation is retried. A failed prerequisite stops later steps and records the failure plus all unrun steps. A necessary repair gets a new disclosed revision, with the first attempt retained. No model is called. No second independent workspace, manual survey or restart is involved. Fresh session state expires under the host's normal idle TTL.
