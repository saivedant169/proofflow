# Workflow comparison v1 protocol

This builder-run probe asks whether ProofFlow adds anything to a competent full recalculation of a small CSV close. It measures reuse of published calculation artifacts, the scope of validation and verification work, and safeguards at the point of report handoff. The nine orders and three reporting regions are fictional. The probe holds the calculations and inputs constant and exercises one sequential workflow per method. It provides no measurements of analyst time, adoption, latency, cost, throughput, or generalization to other workloads.

## Frozen inputs and expected arithmetic

Both methods receive the exact [base CSV](../fixtures/workflow_comparison/base.csv), [corrected CSV](../fixtures/workflow_comparison/refund-corrected.csv), explicit FX strings and selected region `NORTH` from the [case manifest](../fixtures/workflow_comparison/cases.json). Run the cases in order in one fresh workspace per method. “Cold” means the workspace has no prior imported reports. The HydraDB service can already be running. “Warm” means a prior accepted source revision and its published reports exist. It describes workspace history and makes no claim about caches or timing.

The oracle is hand-specified in the case manifest and used unchanged for both arms. It covers gross, refunds, net, converted regional totals, company total, ticket counts, and the two report claims. Check currencies on gross, refunds, and net evidence and the units of both reports. Group native cents by region, subtract refunds, and convert each region once with decimal rounding half to even. Sum the converted regional cents for the company. The frozen check for WEST is `(13,100 − 598) × 1.25 = 15,627.5`, rounded to 15,628 cents. NORTH stays numerically unchanged after the SOUTH refund. ## Methods

**Ordinary full recalculation.** Use a small Python standard-library CSV/Decimal program, with no ProofFlow imports in its arithmetic or version checks. Each source revision recomputes all eight logical outputs from scratch. Use one row scan to parse, validate, and accumulate gross, refunds, net controls, and ticket counts. Check schema and row shape, duplicate identifiers, valid regions and currencies, row and input bounds, refunds within gross, explicit rates, and the selected region. Reconcile each grouped net against the sum of row-level net, the summed support against the input control total, and both report claims against the converted totals. Reuse that validated in-memory calculation during publication, and do one company and one regional report snapshot for each revision. The shared-folder convention saves immutable input revisions and timestamped report files, includes the input revision digest in each report, and compares it with the shared latest input revision and exact current report bytes before handing off a working copy as current. The simulated shared pointer is atomic with a single writer. This is a competent version-aware baseline for the ordered events below. It is no test of concurrent writers or crash recovery.

**ProofFlow.** Use the checked-out FastAPI app and runtime, a new temporary local state directory, and new owned workspace IDs against the running pinned HydraDB OSS service. Use the same app routes as the CSV workspace, with two clients sharing one session cookie and keeping separate view state. Follow `preview → create` for the initial import and `preview → update → refresh` for each correction. The separate preview is part of the browser path and is included even though create/update repeats validation. Record the route that seeds the guided demo separately as cold-start overhead, then execute the same checked export route used for file downloads. Observe the app’s preflight, recorded, and verification counters, and independently tally analytics calls on the original methods with observational wrappers. Keep operation logs, emitted receipts, native dependency paths, current artifact IDs, counts, and outcomes. Static file integrity and observer evidence reads are separate measurements. No arithmetic implementation replacement, simulated graph, fallback, fault injection, or model call is part of the probe.

The freeze records hashes for the protocol, fixtures, checked-out runtime files, and comparison runner before invoking either arm. The runner retains each attempt directory and its terminal status, including failures, with each request’s status and the observations available at that point. A run uses one instance of each arm. Reruns require a new attempt directory and an explanation in the results. Report results as pass, fail, or unobserved at the scheduled checks. An arm must match the frozen oracle to qualify for comparison of its completed outputs. No workload replacement or outcome-based case exclusion is permitted.

## Ordered handoff checks

1. Publish the first version. Check all eight outputs and save the generated company-plus-region handoff. Client A keeps the baseline report working copy and ProofFlow report IDs. Client B owns both incoming corrections and refreshes. Repeat the same handoff sequence after each correction.
2. Accept the corrected shared source revision and pause at the deterministic boundary before the new report is published. On the full recalculation arm this is after the latest-source pointer moves, with the previous report file still available. On the ProofFlow arm it is after `/api/import/update` returns. Client A tries to hand off its previous view as current. Check whether the ordinary version guard rejects it and whether ProofFlow returns HTTP 409 without report payload. Also read fresh ProofFlow state and check whether both noncurrent report claims withhold current values, including the unchanged NORTH amount in the refund correction. The boundary is a scripted workflow state and has no duration target.
3. On ProofFlow inspect the frozen affected output set and follow a native path from the superseded source through alternating execution/artifact nodes to each superseded report. Validate each path edge against the native graph state and/or its persisted producing receipt. Count which heads and receipt IDs survive the correction, and which new tool calls published results. The ordinary workflow records the whole input revision and control totals for its full run. Its baseline avoids schema-specific lineage tracking and so provides only the revision-level provenance actually recorded.
4. Publish the full recalculation and refresh ProofFlow. Check all eight outputs against the same oracle, ensure the stale cached request is still rejected, reload A’s view or select the new current ordinary file, and accept the two corrected claims for handoff. Check prior handed-off bytes and digests after the corrections. A static snapshot in each workflow should remain readable and unchanged. Compare the timestamp/provenance labeling and distinguish it from a new current handoff. The ordinary shared-folder guard needs access to the latest shared revision. Neither exported file is a live report.

## Measurements and interpretation

- **Correctness and scope.** Report exact per-phase values and all eight semantic comparisons. Count ordinary fresh logical output computations and input row scans. Count ProofFlow distinct recorded artifact outputs and retained heads, and give the full breakdown of registered arithmetic invocations by preflight, recorded execution and fresh-recipe verification. Count demo bootstrap separately and show its contribution to first use. Report ordinary reconciliation controls and both methods’ observer oracle checks. Ordinary logical outputs may be produced in one loop. The counts convey what was recomputed, retained or verified in each implementation and do not measure relative compute cost.
- **Handoff.** Report each stale and current attempt, whether amounts were returned, and whether the old static files retained their bytes. Compare the automatic evidence and the explicit version-check convention on their observed behavior. A guard succeeding for both methods is a valid result. Avoid treating the existence of a historical file as a failure of ordinary recalculation or ProofFlow.
- **Decision rule.** A differentiation claim requires a measured difference in recorded graph lineage or retained published work with correct values. If both approaches enforce the ordered handoff check, report equal prevention in that sequence. If ProofFlow’s validation and verification outweigh selective recomputation in measured invocations, show the total openly and avoid a savings claim. The small fixed dataset, two corrections, single run, API clients, and authored scenarios limit interpretation. The results describe the needs of a buyer deciding between fresh, versioned small-file close and automatically tracked artifact-level dependencies.
